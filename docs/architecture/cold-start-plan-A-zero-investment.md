# 冷启动方案 A：0 投入

- 关联：技术方案 report-v3 第 4.2 节、PR #47、#1
- 状态：待真人选择（与方案 B 二选一，或按阶段切换）
- 费用：0 元

## 1. 目标
在不产生任何费用、不办理备案与资质的前提下，完成玩法、动画和题库的内部验证，为是否切换到方案 B 提供依据。

## 2. 范围
- 只做内部开发与测试，不对外提供服务。
- 访问对象：项目组成员与真人指定的少量内部试玩人员（不超过 20 人，不是学生）。
- 不使用真实学生数据，只使用合成数据（由设计与开发准备）。

## 3. 技术方案（零成本）
| 组件 | 方案 | 费用 |
| --- | --- | --- |
| 代码与任务 | GitHub 私有仓库 | 0 元 |
| 后端与数据库 | 本地 Docker（MySQL、Redis 等） | 0 元 |
| Web 预览 | GitHub Pages 或 Cloudflare Pages，仅供内部链接访问（不备案，不对外宣传） | 0 元 |
| 客户端 | Flutter 本地构建，Android 以 APK 形式内部传递，iOS 以 TestFlight 之外的本地方式（不上架） | 0 元 |
| 动画与资源 | 本地素材，Rive 与 Lottie 文件随代码仓库管理 | 0 元 |
| AI 模型 | 不接入，题库与规则判题先行 | 0 元 |

注意：Web 预览的境内访问不保证，仅用于项目组内部。不得在预览页放置真实学生信息或登录入口。

## 4. 验证目标（进入方案 B 的依据）
| 验证项 | 通过标准（待真人确认） |
| --- | --- |
| 单元完成率 | 试玩人员完成一个单元（认词、句型、运用、Boss）的比例不低于 60% |
| 首次体验 | 首次进入后 5 分钟内完成第一个关卡的比例不低于 90% |
| 留存（内部） | 连续 3 天每天至少完成一轮的比例不低于 40% |
| 趣味评分 | 试玩人员对“有没有想再玩”的平均评分不低于 4 分（5 分制） |
| 教学覆盖 | 覆盖率审计通过：单元的词汇、句型、语法、听说项目全部映射到关卡 |
| 技术稳定性 | 关卡加载与动画播放无明显卡顿（在中低端机上做 PoC） |

## 5. 时间与里程碑
| 周次 | 里程碑 | 负责 |
| --- | --- | --- |
| 第 1–2 周 | Unit 1 纵切：认词关、句型关、Boss 与动画各一段，本地可玩 | 项目总监（设计、开发、运营准备） |
| 第 3–4 周 | Unit 2–3 扩展，复习关上线，覆盖率审计 | 项目总监 |
| 第 5–6 周 | 内部试玩（不超过 20 人），收集数据 | 项目总监 + 真人组织试玩 |
| 第 7 周 | 汇总验证结果，提交真人决定是否切换到方案 B | 项目总监 |

## 6. 风险与应对
| 风险 | 应对 |
| --- | --- |
| 验证人数少，结论偏差 | 每个单元至少 5 人试玩，结论只作为是否切换的参考，不作为效果承诺 |
| 内部预览被外部访问 | 设置访问口令；不放真实数据；不对外公布链接 |
| 上线时间推迟 | 方案 B 的备案在验证期间不启动，因此不会在验证阶段产生费用 |

## 7. 切换到方案 B 的条件
同时满足以下三条，才启动方案 B：
1. 真人对设计稿定稿（stage:design-final 之后的确认）；
2. 第 4 节的验证目标全部通过；
3. 法务确认备案方案与未成年人规则（见 report-v3 第 5.1 节）。

## 8. 真人需要决定的事
- 选择方案 A 作为当前阶段。
- 确认第 4 节的验证通过标准。
- 确认内部试玩人员名单（不超过 20 人）。
