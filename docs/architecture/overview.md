# 乐乐学 总体技术方案（v2 草案）

状态：草案，待技术总监审核（对应 issue #1）
更新：v2 纳入 AI、游戏化与动画、题库
负责人：架构师（汇报产品设计师）；审核：技术总监

## 1. 目标

- 玩中学：学习内容以游戏关卡呈现，动画与游戏机制承载知识点。
- 与中国大陆最新人教版内容一致，可以替代课本开展教学。
- 五个学科子系统（英语、数学、语文、物理、化学）同步开发、独立部署、独立迁移，用户身份互通。
- 从初稿到高并发上线，不修改业务代码，只通过配置和扩容实现。
- AI 作为能力提供方，服务于出题、讲解、批改和个性化推荐。面向学生的内容必须经过知识点校验和人工审核。

## 2. 总体架构

```
 Flutter 客户端（Android / iOS / Web）        微信小程序 / 公众号（入口导流）
                 │                                      │
                 └──────── API 网关（鉴权、限流、路由）────────┘
                                      │
  ┌─────────────┬──────────────┬───────┴────────┬────────────────┬────────────────┐
 共享身份服务   共享题库服务     共享 AI 网关      共享游戏化服务    共享内容服务
 (identity)   (question-bank) (ai-gateway)    (gamification)   (content)
                                      │
  ┌──────────┬──────────┬──────────┬┴─────────┬──────────┬──────────┐
 英语服务    数学服务    语文服务    物理服务    化学服务    （各学科独立数据库）
                                      │
              事件总线（答题、通关、升级、成就、掌握度变化）
                                      │
           数据平台（实时统计、掌握度计算、学情报告、离线分析）
```

要点：

- **共享能力**：身份、题库、AI 网关、游戏化、内容管理。它们与具体学科无关，用学科编码区分数据，所有学科共用。
- **学科服务**：只负责本学科的关卡流程和学习进度，数据库独立，不直接访问其他学科的数据。
- **事件总线**：答题、通关、升级、成就都作为事件发布，数据平台和其他服务按需订阅。

## 3. 客户端与游戏化

### 3.1 客户端
- **主端：Flutter**，覆盖 Android、iOS 和 Web，承载完整游戏。
- **入口端：微信小程序 + 公众号**，负责引导、导流、进度查看和提醒，不承载完整游戏。
- 两端共用后端 API 和共享身份服务，学习数据统一存储。

### 3.2 游戏与动画技术选型（待 PoC 验证）

| 用途 | 建议 | 说明 |
| --- | --- | --- |
| 游戏循环、角色、碰撞 | Flame（Flutter 2D 游戏引擎） | 适合闯关类玩法，与 Flutter 原生集成 |
| 可交互动画（状态机） | Rive | 角色动作随答题结果切换，如答对、答错、升级 |
| 一次性动效 | Lottie | 成就弹窗、奖励动画等 |
| 音效 | Flutter 音频库 | 统一封装为游戏音效服务 |

### 3.3 游戏化机制
- 经验、等级、徽章、关卡解锁规则全部用配置表管理，不写死在代码中，便于调整手感。
- 每个关卡绑定一组知识点编码，通关条件与掌握度挂钩。
- 动画文件、关卡配置、音效按版本发布到对象存储，通过 CDN 分发，客户端按需下载。

## 4. 题库服务（共享）

### 4.1 题目模型
- 学科、学段、年级、册次、单元、知识点编码（对应人教版教材）
- 题型（选择、填空、解答、口语、作文等）、难度、题干、选项、答案、解析
- 来源（人工编写 / AI 生成 / 教材原题）、版本号、审核状态

### 4.2 入库流程

```
AI 或人工出题 → 自动校验（格式、知识点、答案一致性、超纲检测）
              → 人工审核（抽检，重点题全审）→ 发布 → 版本化入库
```

- 未通过审核的题目不能进入学生可见的题库。
- 所有题目保留生成记录，便于追溯和修正。

### 4.3 检索与存储
- 题目主数据存 MySQL，按学科和知识点分片。
- 按知识点与难度检索使用缓存和索引，热门题目放入 Redis。
- 题目相似检索（如"找与这道题相似的题"）使用向量索引，作为后期能力。

## 5. AI 网关（共享）

### 5.1 职责
- 统一对接多个大模型供应商，业务服务不直接调用模型。
- 提示词模板版本化管理，支持灰度切换。
- 知识库检索（RAG）：把人教版教材内容切分入库，AI 回答必须基于检索到的教材内容。
- 限流、计费、缓存、超时与降级。
- 安全过滤与审计日志，供合规审查。

### 5.2 调用分级（控制成本与延迟）

| 级别 | 场景 | 方式 |
| --- | --- | --- |
| 规则与题库 | 普通判题、常见错误提示 | 不调用模型 |
| 小模型 | 简单讲解、短文本反馈 | 实时调用，结果缓存 |
| 大模型 | 作文点评、口语评估、复杂解析 | 异步队列处理，结果回写 |

### 5.3 模型部署原则（已决策）
- **私有化部署优先**：学生数据（对话、答题记录、学习行为）只能由私有化部署的模型处理，不发送给外部 API。
- 私有化推理服务使用 vLLM，对外提供 OpenAI 兼容接口，AI 网关只配置内部地址。
- 初期使用云上按量付费的 GPU，调用量稳定后再评估自有设备。
- 公有 API 仅用于教材原文、人工编写内容的离线生成，且不涉及学生个人信息。
- 模型选型以许可证（商用条款）和中文能力为主要标准，上线前按当时的榜单与许可证重新核对。

### 5.4 典型应用
- **智能出题**：异步批量生成，进入题库审核流程。
- **即时讲解**：学生答错后实时生成提示，不直接给出答案。
- **作文与口语**：异步批改，完成后推送结果。
- **学情报告**：定时生成，供家长和老师查看。

### 5.5 降级策略
AI 服务不可用或超时时：
- 讲解类功能回退到题库中预置的标准解析。
- 批改类功能提示"稍后查看"，任务进入队列重试。
- 游戏主流程不依赖 AI，学生可以正常闯关。

## 6. 学习数据与掌握度

- 答题、通关、使用提示等行为作为事件写入事件总线。
- 数据平台按知识点计算掌握度（基于正确率、间隔和难度等因素），结果回写到学科服务，用于推荐下一关。
- 实时指标（在线人数、当日答题量）与离线分析（学情报告、教学效果）分开处理。

## 7. 高并发与大数据

| 层次 | 方案 | 说明 |
| --- | --- | --- |
| 服务 | 无状态服务，水平扩展 | 会话放 Redis，实例可随时增减 |
| 缓存 | Redis 集群 | 题目、关卡配置、排行榜、会话 |
| 数据库 | MySQL，按用户ID或学科分库分表 | 初期单库，分片键预留扩展 |
| 消息 | RocketMQ 或 Kafka | 削峰、解耦、事件分发、AI 异步任务 |
| 资源 | 对象存储 + CDN | 动画、音频、图片 |
| 分析 | 实时计算 + 离线数仓 | 掌握度、学情报表 |

**"不改代码扩容"的保证方式**
1. 数据访问统一通过仓储接口，分片规则由配置决定。
2. ID 使用全局唯一生成器（如雪花算法）。
3. 连接池、缓存地址、模型供应商、限流阈值全部来自配置。
4. 中间件和模型供应商都通过适配层接入，切换实现只改配置。

## 9. 合规与安全

- **学生数据只走私有化模型**：学生身份、学校、联系方式、家长信息不进入任何大模型；学生对话、答题记录、学习行为只能由私有化部署的模型处理。
- **未成年人数据**：最小化收集，敏感信息加密，学生对话记录脱敏，不用于训练外部模型。
- **生成式 AI 服务**：面向公众提供的生成式 AI 服务，需按国家规定履行备案等义务。具体要求由法务确认。
- **内容安全**：AI 输出经过安全过滤，学生可见内容必须经过人工审核。
- **个人信息保护**：隐私政策、用户授权、数据留存期限由法务审核。

## 10. 迭代计划（建议）

1. **阶段一（可玩原型）**：选一个学科（建议数学），跑通关卡、动画、题库和规则判题，暂不接入 AI。
2. **阶段二（接入 AI）**：接入 AI 网关，上线智能出题（经审核入库）和即时讲解，并建立降级策略。
3. **阶段三（扩展学科）**：其余学科复用共享服务，各自实现关卡和内容；上线小程序入口。
4. **阶段四（高并发与数据）**：拆分服务、接入消息队列和缓存，完成压测；启用分库分表和弹性扩容。

3. 云服务商与预算。

## 12. 与子系统的关系

- 五个学科的架构师，基于本方案给出各自的关卡设计、题库接入和 AI 调用方案（对应 issue #8、#11、#14、#17、#20）。
- 产品设计师需要明确每个关卡的知识点编码、题型和动画需求，作为题库与动画资源的输入。
- 本方案通过审核后，子系统才进入实现阶段。
