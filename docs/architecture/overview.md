# 乐乐学 总体技术方案（初稿）

状态：草案，待技术总监审核（对应 issue #1）
负责人：架构师（汇报产品设计师）；审核：技术总监

## 1. 设计目标

- 一套架构同时支持微信小程序、Android、iOS、Web。
- 架构从初稿起就按大数据与高并发设计。从初稿到并发上线，不需要修改业务代码，只通过配置和部署扩容。
- 五个学科子系统（英语、数学、语文、物理、化学）同步开发、独立部署、独立迁移。
- 用户账号与身份在五个子系统之间互通；学习数据按子系统独立存储。
- 内容与中国大陆最新人教版教材保持一致，可以完整替代课本教学。

## 2. 总体架构

```
 微信小程序 / Android / iOS / Web（同一套客户端代码）
                     │
                 API 网关（统一鉴权、限流、路由）
                     │
  ┌──────────┬───────┴───────┬──────────┬──────────┬──────────┐
 共享身份服务  英语服务   数学服务   语文服务   物理服务   化学服务
 (identity)  (english)   (math)   (chinese)  (physics) (chemistry)
     │           │          │          │          │          │
  用户库      英语库      数学库     语文库     物理库     化学库
                     │
            事件总线（消息队列）── 跨子系统事件（如"升级""成就"）
                     │
          数据与分析（离线计算、掌握度统计、运营报表）
```

要点：

- **共享身份服务（identity）**：统一用户ID、登录、会话、基础资料（昵称、头像、年级）。五个子系统只读取，不各自维护用户表。
- **学科服务**：每个学科一套服务和一个数据库，只通过网关和事件总线与外界通信，不直接访问其他学科的数据。
- **事件总线**：学科服务把"学习进度变化""升级""获得成就"等事件发布出去，其他服务按需订阅，实现跨学科的统一成长视图。

## 3. 客户端与跨端方案

- **推荐方案：uni-app（Vue 语法）**。一套代码输出微信小程序、Android、iOS 和 H5（Web）。在国内生态中覆盖面广，原生能力可通过插件扩展。
- 候选方案：Taro（React 语法），同样支持多端输出。
- 游戏化界面（关卡地图、动画、音效）统一封装为公共组件库，放在 `packages/shared`。
- 需要决策：是否对 Android/iOS 做原生性能优化（如复杂动画）。初期不做，有性能瓶颈后再评估。

## 4. 高并发与大数据路线

| 层次 | 方案 | 说明 |
| --- | --- | --- |
| 服务 | 无状态服务，水平扩展 | 会话放 Redis，服务实例可随时增减 |
| 缓存 | Redis 集群 | 热点内容、排行榜、用户会话 |
| 数据库 | MySQL，按用户ID分库分表 | 初期单库即可，通过分片键预留扩展，不改业务代码 |
| 消息 | 消息队列 | 削峰、解耦、跨子系统事件 |
| 内容 | 对象存储 + CDN | 图片、音频、视频等静态资源 |
| 分析 | 离线数仓（后期） | 掌握度统计、学情报表，不影响在线业务 |

**"不改代码扩容"的保证方式**：

1. 数据访问统一通过仓储接口，分片规则由配置决定。
2. 所有 ID 使用全局唯一ID生成器（如雪花算法），不依赖数据库自增。
3. 服务启动参数、连接池、缓存地址全部来自配置。
4. 依赖的中间件（数据库、缓存、队列）都通过适配层接入，切换实现只改配置。

## 5. 技术选型（待确认）

| 领域 | 建议 | 备选 | 说明 |
| --- | --- | --- | --- |
| 客户端 | uni-app | Taro | 多端覆盖最全 |
| 后端语言 | Java（Spring Boot） | Go | 生态成熟，人才多，适合大型业务 |
| 数据库 | MySQL | PostgreSQL | 团队熟悉、生态成熟 |
| 缓存 | Redis | — | 行业标准 |
| 消息队列 | RocketMQ 或 Kafka | — | 国内场景成熟，支持高吞吐 |
| 部署 | Docker + Kubernetes | — | 上线后弹性扩缩容 |
| 网关 | Spring Cloud Gateway 或 Nginx + 自研鉴权 | — | 统一入口 |

## 6. 知识点与内容模型

- 按人教版教材的 **学段 → 年级 → 册 → 单元 → 课 → 知识点** 层级建模。
- 每个知识点有唯一编码（学科 + 学段 + 册次 + 序号），便于校对与统计。
- 游戏化关卡引用知识点编码，关卡内容与教材版本绑定，教材更新时只更新内容包，不改代码。
- 内容以版本化的数据包形式发布（如 JSON），由内容管理后台维护。

## 7. 用户数据与隐私

- 账号、基础资料在共享身份服务中统一保存。
- 学习记录（关卡进度、答题、掌握度）按学科独立存储，并带学科标识。
- 未成年人数据按相关法规处理，最小化收集，敏感信息加密存储。

## 8. 迭代计划（建议）

1. **阶段一（初稿）**：单体部署在一套环境中，但代码已按子系统和服务边界划分，数据访问已通过仓储接口。
2. **阶段二（上线前）**：拆分为独立服务，接入消息队列和缓存，完成压测。
3. **阶段三（并发上量）**：启用分库分表和弹性扩容，仅调整配置。

## 9. 待真人决策的事项

1. 后端语言选 Java 还是 Go。
2. 客户端框架选 uni-app 还是 Taro。
3. 云服务商与预算。
4. 首批覆盖的学段与年级。
5. 是否需要 Android/iOS 原生性能优化。

## 10. 与子系统的关系

- 本方案通过审核后，子系统才进入实现阶段。
