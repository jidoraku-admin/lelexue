## 1. 目标

- 玩中学：学习内容以游戏关卡呈现，动画与游戏机制承载知识点。
- 与中国大陆最新人教版内容一致，可以替代课本开展教学。
- 五个学科子系统（英语、数学、语文、物理、化学）同步开发、独立部署、独立迁移，用户身份互通。
- 从初稿到高并发上线，不修改业务代码，只通过配置和扩容实现。
- AI 作为能力提供方，服务于出题、讲解、批改和个性化推荐。面向学生的内容必须经过知识点校验和人工审核。

## 2. 总体架构

```
 Flutter 客户端（Android / iOS / Web）        微信小程序 / 公众号（入口导流）
                 │                                      │
                 └──────── API 网关（鉴权、限流、路由）────────┘
                                      │
  ┌─────────────┬──────────────┬───────┴────────┬────────────────┬────────────────┐
 共享身份服务   共享题库服务     共享 AI 网关      共享游戏化服务    共享内容服务
 (identity)   (question-bank) (ai-gateway)    (gamification)   (content)
                                      │
  ┌──────────┬──────────┬──────────┬┴─────────┬──────────┬──────────┐
 英语服务    数学服务    语文服务    物理服务    化学服务    （各学科独立数据库）
                                      │
              事件总线（答题、通关、升级、成就、掌握度变化）
                                      │
           数据平台（实时统计、掌握度计算、学情报告、离线分析）
```

- **共享能力**：身份、题库、AI 网关、游戏化、内容管理。与学科无关，用学科编码区分数据，由共享能力架构师（issue #23）负责。
- **学科服务**：只负责本学科的关卡流程和学习进度，数据库独立，不直接访问其他学科的数据。
- **事件总线**：答题、通关、升级、成就作为事件发布，数据平台和其他服务按需订阅。

## 3. 客户端与游戏化

### 3.1 客户端
- **主端：Flutter**，覆盖 Android、iOS 和 Web，承载完整游戏。
- **入口端：微信小程序 + 公众号**，负责引导、导流、进度查看和提醒，不承载完整游戏。
- 两端共用后端 API 和共享身份服务，学习数据统一存储。

### 3.2 游戏与动画选型（待 PoC 验证）

| 用途 | 建议 | 说明 |
| --- | --- | --- |
| 游戏循环、角色、碰撞 | Flame | 适合闯关类玩法，与 Flutter 原生集成 |
| 交互动画（状态机） | Rive | 角色动作随答题结果切换 |
| 一次性动效 | Lottie | 成就弹窗、奖励动画 |
| 音效 | Flutter 音频库 | 统一封装为游戏音效服务 |

### 3.3 游戏化机制
- 经验、等级、徽章、关卡解锁规则全部用配置表管理，便于调整手感。
- 每个关卡绑定一组知识点编码，通关条件与掌握度挂钩。
- 动画、关卡配置、音效按版本发布到对象存储，经 CDN 分发，客户端按需下载。

## 4. 题库服务（共享）

### 4.1 题目模型
- 学科、学段、年级、册次、单元、知识点编码（对应人教版教材）
- 题型、难度、题干、选项、答案、解析
- 来源（人工 / AI 生成 / 教材原题）、版本号、审核状态

### 4.2 入库流程
```
AI 或人工出题 → 自动校验（格式、知识点、答案一致性、超纲检测）
              → 人工审核（抽检，重点题全审）→ 发布 → 版本化入库
```
- 未通过审核的题目不能进入学生可见的题库。
- 所有题目保留生成记录，便于追溯和修正。

### 4.3 检索与存储
- 题目主数据存 MySQL，按学科和知识点分片。
- 热门题目与检索结果放入 Redis。
- 相似题检索使用向量索引，作为后期能力。

## 5. AI 网关与私有化部署（共享）

### 5.1 职责
- 统一对接模型服务，业务服务不直接调用模型。
- 提示词模板版本化，支持灰度切换。
- RAG：人教版教材切分入库，AI 回答基于检索到的教材内容。
- 限流、计费、缓存、超时与降级；安全过滤与审计日志。

### 5.2 部署原则（已确定）
- **私有化部署优先**：学生身份、学校、联系方式、家长信息不进入任何模型；学生对话、答题记录、学习行为只由私有化模型处理。
- 推理服务使用 vLLM，对外提供 OpenAI 兼容接口，AI 网关只配置内部地址。
- 公有 API 仅用于教材原文、人工编写内容的离线生成，且不涉及学生个人信息。
- 模型选型以许可证（商用条款）和中文能力为主，上线前按当时榜单与许可证重新核对。

### 5.3 调用分级（控制成本与延迟）

| 级别 | 场景 | 方式 | 目标占比 |
| --- | --- | --- | --- |
| 规则与题库 | 普通判题、常见错误提示、标准解析 | 不调用模型 | 约 60% |
| 缓存 | 相同题目的讲解复用 | 命中缓存 | 约 20% |
| 小模型 | 简单讲解、短文本反馈 | 实时调用 | 约 15% |
| 大模型 | 作文点评、口语评估、复杂解析 | 异步队列处理 | 约 5% |

### 5.4 典型应用
- **智能出题**：异步批量生成，进入题库审核流程。
- **即时讲解**：答错后实时生成提示，不直接给答案。
- **作文与口语**：异步批改，完成后推送结果。
- **学情报告**：定时生成，供家长和老师查看。

### 5.5 降级策略
- 讲解类功能回退到题库预置的标准解析。
- 批改类功能提示"稍后查看"，任务进入队列重试。
- 游戏主流程不依赖 AI，学生可以正常闯关。

## 6. 学习数据与掌握度
- 答题、通关、使用提示等行为作为事件写入事件总线。
- 数据平台按知识点计算掌握度（基于正确率、间隔和难度），结果回写学科服务，用于推荐下一关。
- 实时指标与离线分析分开处理。

## 7. 高并发与扩容原则

| 层次 | 方案 | 说明 |
| --- | --- | --- |
| 服务 | 无状态服务，水平扩展 | 会话放 Redis |
| 缓存 | Redis | 题目、关卡配置、排行榜、会话 |
| 数据库 | MySQL，按用户ID或学科分库分表 | 初期单库，分片键预留 |
| 消息 | RocketMQ 或 Kafka | 削峰、事件分发、AI 异步任务 |
| 资源 | 对象存储 + CDN | 动画、音频、图片 |
| 分析 | 实时计算 + 离线数仓 | 掌握度、学情报表 |

**"不改代码扩容"的保证方式**
1. 数据访问统一通过仓储接口，分片规则由配置决定。
2. ID 使用全局唯一生成器（如雪花算法）。
3. 连接池、缓存地址、模型地址、限流阈值全部来自配置。
4. 中间件和模型服务都通过适配层接入，切换实现只改配置。

**扩容触发条件（建议，待运维确认）**
- 应用服务器 CPU 持续超过 60%，或响应时间 P95 超过 500 毫秒。
- 数据库连接数超过阈值的 70%，或主库写入延迟升高。
- GPU 推理排队时间超过 2 秒。
- CDN 或公网带宽使用率超过 70%。

## 9. 基础设施与投入规划

### 9.1 估算假设（需用真实数据校准）

| 假设 | 数值 |
| --- | --- |
| 峰值并发 | 日活用户的约 10% |
| 请求频率 | 每个在线用户约每 5 秒 1 次 |
| 每用户每日 AI 调用 | 早期 5 次，增长期 8 次，规模期 10 次 |
| 每次 AI 调用平均 token | 约 1,500 |
| 资源流量 | 首次进入约 20MB，之后缓存约 2MB/日 |
| 每用户每日学习数据 | 约 50KB |

### 9.2 分阶段规划

| 项目 | 阶段 0：无用户（开发与内测） | 阶段 1：早期（约 1 千日活） | 阶段 2：增长（约 1 万日活） | 阶段 3：规模（约 10 万日活） |
| --- | --- | --- | --- | --- |
| 环境 | 开发、测试、预发、生产各一套 | 同左 | 同左，生产多可用区 | 同左，生产多可用区 + 灾备 |
| 应用服务器 | 2 台（最小规格） | 3 台 | 6 台 | 20–30 台（弹性伸缩） |
| 数据库 | MySQL 单机 + 备份 | 主从 | 分库 2–4 个，每库主从 | 分库分表 8 个以上，主从 |
| 缓存 | 单实例 | 主从 | 集群 | 集群，多节点 |
| 消息队列 | 单机 | 最小集群 | 集群 | 集群 |
| GPU（私有化推理） | 0，PoC 时临时租用 | 1 卡 | 2–3 卡 | 10–15 卡（以 benchmark 为准） |
| 对象存储 | 约 100GB | 约 500GB | 约 2TB | 10TB 以上 |
| CDN 带宽 | 约 5 Mbps | 20–50 Mbps | 100–200 Mbps | 500 Mbps–1 Gbps |
| API 公网出口带宽 | 约 5 Mbps | 约 10 Mbps | 约 50 Mbps | 200–300 Mbps |
| 峰值 QPS（估算） | 低于 10 | 约 20 | 约 200 | 约 2,000 |
| 每日 AI 调用（估算） | 0 | 约 5,000 | 约 8 万 | 约 100 万（约 20% 落到模型，其余由题库、缓存解决） |
| 安全与监控 | 基础监控、备份 | 日志与告警 | WAF，等保测评 | 完整灾备与演练 |
| 主要成本项 | 服务器最小规格、域名与备案、应用商店账号 | 服务器、数据库、1 张 GPU | GPU、带宽、数据库 | GPU 与带宽为主，成本随用户线性增长 |

### 9.3 投入变化的规律
- **固定成本**：环境、备案、应用商店账号、监控。无用户阶段主要是这部分，金额低。
- **阶梯成本**：应用服务器、数据库、缓存。在用户跨过一个量级时才需要扩容，因此是阶梯式增长。
- **可变成本**：GPU 和带宽。随用户数和调用量线性增长，是后期成本的主要来源。
- **降低成本的关键**：AI 调用中，尽量由题库、缓存和小模型解决，只把少量复杂任务交给大模型。这是 9.2 表中 AI 调用只有约 20% 落到模型的前提。

## 10. 合规与安全

- **学生数据只走私有化模型**：学生身份、学校、联系方式、家长信息不进入任何模型；学生对话与学习行为只由私有模型处理。
- **未成年人数据**：最小化收集，敏感信息加密，学生对话记录脱敏，不用于训练外部模型。
- **生成式 AI 服务**：面向公众提供服务时，需按国家规定完成备案。具体要求由项目方自行核对落实。
- **个人信息保护**：隐私政策、用户授权、数据留存期限由项目方自行制定并落实。
- **等级保护**：教育类信息系统的等级保护要求，由运维确认等级并在上线前完成测评。
- **内容安全**：AI 输出经过安全过滤，学生可见内容必须经过人工审核。

## 11. 迭代计划（与基础设施阶段对应）

| 阶段 | 对应基础设施 | 目标 |
| --- | --- | --- |
| 阶段 0：可玩原型 | 阶段 0 | 选数学学科，跑通关卡、动画、题库和规则判题，暂不接入 AI |
| 阶段 1：接入 AI | 阶段 0 → 1 | 接入私有化模型，上线智能出题（经审核入库）和即时讲解，建立降级策略 |
| 阶段 2：扩展学科 | 阶段 1 → 2 | 其余学科复用共享服务，上线小程序入口 |
| 阶段 3：高并发与数据 | 阶段 2 → 3 | 拆分服务、接入消息队列和缓存，完成压测，启用分库分表和弹性扩容 |

## 12. 与子系统的关系

- 五个学科的架构师（#8、#11、#14、#17、#20）基于本方案给出关卡设计、题库接入和 AI 调用方案。
- 共享能力架构师（#23）负责身份、题库、AI 网关、游戏化组件等共享能力。
- 产品设计师需要明确每个关卡的知识点编码、题型和动画需求，作为题库与动画资源的输入。
- 本方案通过确认后，子系统才进入实现阶段。
