> 负责：共通对话（共享能力架构师，#23）
> 状态：草案，未经学科对话确认，未经技术总监审核。
> 关联：#1 总体方案、#23 共享能力、#68 六对话协调、`docs/architecture/report-v3.md`、`docs/decisions/0004`、`0006`

## 1. 范围

共享能力与学科无关，只通过学科编码区分数据。五个学科各自独立部署和存储数据，共享以下五类服务：

| 服务 | 草案文档 | 一句话职责 |
| --- | --- | --- |
| 身份 identity | `identity.md` | 统一用户 ID、登录、会话、母子账号与席位 |
| 题库 question-bank | `question-bank.md` | 题目模型、入库、版本化、检索 |
| AI 网关 ai-gateway | `ai-gateway.md` | 模型适配、私有化接入、RAG、限流、降级 |
| 游戏化 gamification | `gamification.md` | 经验、等级、徽章、积分规则与 Flutter 组件 |
| 内容 content | 待写 | 版本化内容包的发布与分发（#23 职责之一，排在后续） |

## 2. 共同约束

1. **学生数据只走私有化模型。** AI 网关不允许把学生数据发往外部模型服务。
2. **学科隔离。** 共享服务只保存与学科无关的身份与规则；学科学习数据（进度、答题记录、掌握度）按学科编码分库或分表存储。
3. **未成年人规则未过法务复核前不上线。** 涉及未成年人的身份、数据收集、消费限制、推送等能力，只做到接口和开关层面，不启用。
4. **规则数值后台配置。** 奖励次数、佣金、积分兑换等数值由后台配置，不写死在代码中（见 0004）。
5. **不做结果承诺。** 接口返回的"等级、徽章"等文案不得暗示考试成绩（见 0002、0006）。
6. **依赖顺序。** 学科对话使用共享能力前，先在 #23 提需求；共通对话回复接口与排期后，学科才能在代码中依赖。

## 3. 待共通对话自审的问题（提交技术总监前）

- 四项接口是否互相循环依赖？（例如题库依赖身份，身份不依赖题库。）
- AI 网关的请求是否都携带学科编码和用户 ID，便于审计与限流？
- 游戏化的事件是否由学科对话上报，而不是由共享服务反向读取学科数据？

## 4. 需要学科对话确认的问题（在 #23 留言）

- 英语：现有 `ProgressStore` 的字段是否能映射到共享身份的"用户 ID + 学科编码"？单词题库的 JSON 结构能否迁移到共享题库？
- 数学、语文、物理、化学：各学科的题型和掌握度字段是否能用同一个题目模型表达？
- 所有学科：是否需要"学习时长"与"答题事件"两类事件进入游戏化？

## 5. 决定分级

- 本草案中的接口字段：共通对话决定，记录在 #23。
- 改变学习路径或游戏机制的部分：项目总监决定，写入每日汇总。
- 学段覆盖范围、未成年人功能、付费、AI 内容策略：真人确认。
