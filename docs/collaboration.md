# 乐乐学 协作约定

适用对象：真人，以及项目总监（由 Claude 担任，唯一的 AI 角色）。
更新日期：2026-11-21
依据：项目说明（项目文档）与本文件。原岗位（五学科产品设计师、架构师、运营，共享能力架构师）全部取消，原岗位职责保留为工作类型。

## 1. 一句话规则

- **任务与状态**在 issue 里沟通。
- **设计和代码的审核**在 PR 里进行。
- **决定**写在 issue 里：总体决定在 #1，学科决定在该学科的 issue 里。
- 对话里得出的结论，必须回写到 issue 或文档中，否则视为未决定。

## 2. 账号与签名

- 所有评论都由同一账号 `jidoraku-admin` 发出，因此靠签名区分工作类型。
- 每条评论第一行必须写签名：`【工作类型｜学科｜issue号】`，例如 `【设计｜英语｜#7】`、`【开发｜数学｜#11】`。
- 工作类型只有四种：设计、开发、运营、能力。

## 3. 角色与职责

| 角色 | 职责 | 汇报对象 |
| --- | --- | --- |
| 真人 | 确认大事，定稿设计，验收最终产品，每天 19 时查看汇总 | — |
| 项目总监（Claude） | 统筹全项目；承担设计、开发、运营、能力四类工作；审核设计稿与 PR；决定中事与小事；维护每日汇总 | 真人 |

工作类型说明：

| 工作类型 | 标签 | 原岗位 | 内容 |
| --- | --- | --- | --- |
| 设计 | `role:设计` | 产品设计师 | 设计产品与游戏化关卡，四维度自审，定稿后交真人 |
| 开发 | `role:开发` | 架构师 | 学科内实现与 GitHub 管理，提 PR |
| 运营 | `role:运营` | 运营 | 真人验收通过后的推广工作 |
| 能力 | `role:能力` | 共享能力架构师（#23） | 身份、题库、AI 网关、游戏化等跨学科共享能力 |

说明：
- 同一条工作只标一个 `role:*` 标签，负责人统一为项目总监。
- 技术可行性由项目总监判断；产品取舍的最终结论交真人确认。

## 4. Issue 的用法

### 4.1 编号对照
- `#1` 乐乐学总体技术方案。
- `#2` 英语、`#3` 数学、`#4` 语文、`#5` 物理、`#6` 化学：学科启动，作为该学科的汇总入口。
- `#7` 至 `#21`：各学科的工作单，标题格式为 `[学科][工作类型] 任务名`。
- `#23`：共享能力，标签为 `role:能力`。
- `#25`：每日汇总。

### 4.2 工作的完整流程
1. 开始工作时在 issue 下留言一句话说明。
2. 交付时，在 issue 下留言，写明交付物路径、PR 编号、需要真人确认的事项。
3. 项目总监审核后，在 issue 下留言结论：通过 / 需修改 / 阻塞。
4. 设计类 issue：项目总监四维度审核通过后，标签改为 `stage:design-final`，交真人定稿；真人确认后进入开发。
   开发类 issue：项目总监审核通过后关闭。

### 4.3 依赖关系（硬性条件）
- 开发任务（#8、#11、#14、#17、#20）必须同时满足：
  1. 对应学科的设计 issue 已通过真人定稿（#7、#10、#13、#16、#19）；
  2. 总体技术方案 #1 已通过。
- 两个条件缺一不可。在此之前只能做调研和草案，不得开始实现。
- 学科开发需要共享能力时，先在 #23 提出需求，由项目总监排期并给出接口后再开工。不得直接修改 `packages/shared/` 下的共享代码。

## 5. PR 的用法

- **分支名**：`feat/<学科>-<主题>-<issue号>`，例如 `feat/english-product-design-7`。
- **PR 标题**：`[学科][工作类型] 内容（状态）`，例如 `[英语][设计] 产品设计与学段梳理（待审核 v1.0）`。
- **文件位置**：产品文档放 `docs/product/`，架构文档放 `docs/architecture/`，学科代码放 `apps/<学科>/`，数据放 `docs/data/`。
- **PR 描述**：写明关联的 issue（使用"Refs #7"，不要用"Closes"，关闭权在项目总监），列出交付清单和需要审核的问题。
- **审核**：项目总监在 PR 中逐项给出结论。涉及大事的 PR 同时需要真人确认。
- **合并**：项目总监合并。合并前完成自审清单（见第 6 节的四维度与本节的检查项）。

## 6. 提问与决定

- **需要决定的事**：在相关 issue 下标注 `needs-decision` 标签。
- **需要真人处理的事**：在相关 issue 下标注 `needs-human` 标签。
- **跨学科问题**：写在 #1 下。
- **决定分级**：
  - **小事**（在已批准的范围内调整关卡数值、文案等）：项目总监决定，在 issue 中记录。
  - **中事**（改变学科的学习路径或游戏机制）：项目总监决定，每天 19 时汇总给真人。
  - **大事**（学段覆盖范围、未成年人相关功能、付费、AI 内容策略）：必须真人确认。
- **真人的审核节奏**：项目总监每天 19 时汇总一次需要真人决定的事项，集中提交。紧急事项除外。
- **需要真人决定的事**：项目总监在 #1 下汇总，列出选项、建议和影响。真人回复后，项目总监把结论写回 #1，并同步更新相关文档。
- **决定的记录**：决定一经做出，写在 issue 评论中，并同步到对应文档（文档中增加"决定记录"段落）。

## 7. @ 提及规则

- 只 `@` 真实的 GitHub 登录名。目前只有 `jidoraku-admin`。
- 角色名、工作类型、学科名不使用 `@`，改用反引号，例如 `项目总监`、`设计`，避免误发通知。
- 需要通知真人时，在 #1 下写明。

## 8. 长内容的发布

- 超过几行的评论，先写入文件，再用 `gh api ... -F body=@文件路径` 发布，不要在命令行中直接拼接长文本。
- 发布后检查一次评论是否完整。若被截断，编辑原评论或发布更正评论，并注明"更正"。

## 9. 阶段接力（学科内）

每个学科的工作按阶段接力，同一时间只有一个阶段生效，由 issue 上的标签决定。

| 阶段 | 标签 | 谁可以动 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 设计中 | `stage:design` | 设计：起草；项目总监：逐轮审核与可行性评估 | 项目总监审核通过，标签改为 `stage:design-final` |
| 待真人定稿 | `stage:design-final` | 真人 | 真人在 issue 中回复「定稿」，标签改为 `stage:dev` |
| 开发中 | `stage:dev` | 开发 | 功能完成，PR 通过审核 |
| 待验收 | `stage:acceptance` | 真人 | 真人验收通过，标签改为 `stage:promotion` |
| 推广中 | `stage:promotion` | 运营 | — |

**硬性规则**
- 没有真人定稿（`stage:design-final` 之后的确认），不得开始开发，不得提交功能 PR。
- 没有真人验收通过，不得开始推广。
- 阶段只能向前推进。回退需要在 issue 中说明原因，并由真人确认。

**设计稿的审核标准**
项目总监审核每一版稿件时，从以下四个维度给出结论：

| 维度 | 审核要点 |
| --- | --- |
| 技术 | 能否在 Flutter、Flame、Rive、Lottie 上实现；依赖的共享服务是否已就绪；AI 调用是否符合分层（题库、缓存、小模型、大模型）；工作量估计与风险 |
| 趣味 | 游戏循环是否清楚；玩家每 5–10 分钟是否有明确小目标；升级、奖励、反馈是否及时；是否真的在玩，而不是换了皮的做题 |
| 故事 | 是否有统一的世界观和角色；关卡之间是否有连贯的剧情线；故事是否服务于知识点 |
| 吸引性 | 目标用户（学段、年龄）是否清楚；首次体验能否在几分钟内获得成就感；留存机制是否合理，且不依赖诱导或成瘾设计 |

**结论格式**：每一版审核在 issue 中给出四个维度的结论（通过 / 需修改 / 不可行），并列出具体修改点。四个维度都通过，才能进入 `stage:design-final`。

**定时任务的执行方式**：学科定时任务每次运行时先读取当前阶段标签，只执行该阶段对应的工作，阶段不符的直接跳过，不留下空的留言。
