## 1. 一句话规则

- **任务与状态**在 issue 里沟通。
- **设计和代码的审核**在 PR 里进行。
- **决定**写在 issue 里：总体决定在 #1，学科决定在该学科的 issue 里。
- 对话里得出的结论，必须回写到 issue 或文档中，否则视为未决定。

## 2. 当前账号说明（重要）

- 目前所有岗位的 GitHub 评论都由同一个账号 `jidoraku-admin` 发出。所以**不能靠发帖人判断岗位**。
- 每条评论的第一行必须写签名：`【角色｜学科｜issue号】`，例如 `【产品设计师｜英语｜#7】`。
- 指派（assignee）只表示"由谁跟进"，不代表"由谁决定"。决定权以第 3 节的汇报关系为准。
- 如果某个岗位改用独立账号，更新本文件并在 #1 中通知。

## 3. 角色与汇报关系

| 角色 | 职责 | 汇报对象 | 主要沟通位置 |
| --- | --- | --- | --- |
| 真人 | 协助 AI 无法完成的操作与审核，验收最终产品 | — | issue #1 或直接对话 |
| 项目总监 | 统筹全项目，评估产品方案的可行性与最优化，审核架构方向 | 真人 | 学科 issue 的审核，PR 中的结论 |
| 产品设计师 | 设计产品与游戏化关卡，与项目总监探讨可行性与优化，最终结论上报真人 | 项目总监（过程），真人（最终结论） | 本学科的岗位 issue，产品文档的 PR |
| 架构师 | 负责 GitHub 管理与功能实现 | 项目总监 | 本学科的岗位 issue，代码 PR |
| 共享能力架构师（专岗） | 负责身份、题库、AI 网关、游戏化组件等跨学科共享能力 | 项目总监 | issue #23，共享能力的 PR |
| 运营 | 负责推广 | 真人 | 本学科的岗位 issue，运营文档 PR |

说明：
- 产品设计师不向架构师下达产品决定。产品方案的可行性由项目总监与产品设计师共同评估，最终结论上报真人确认。
- 架构师直接向项目总监汇报，实现方案由项目总监审核。
- 项目总监直接向真人汇报，所有总体决定由真人确认。
- 产品设计师与架构师可以在学科 issue 中直接讨论技术可行性与产品约束。出现分歧时，由项目总监介入裁决。
- 运营可以在学科 issue 中向产品设计师提问，产品设计师的回复视为正式输入。
- 共享能力架构师只负责跨学科的共享部分，学科内的实现仍由各学科架构师负责。

## 4. Issue 的用法

### 4.1 编号对照
- `#1` 乐乐学总体技术方案。
- `#2` 英语、`#3` 数学、`#4` 语文、`#5` 物理、`#6` 化学：学科启动（不做具体任务，只作为该学科的汇总入口）。
- `#7` 至 `#21`：各岗位的任务单，标题格式为 `[学科][岗位] 任务名`，标签为 `role:<岗位>`。
- `#23`：共享能力架构师（跨学科专岗），标签为 `role:共享能力架构师`。

### 4.2 岗位任务的完整流程
1. 岗位在自己的 issue 下开始工作，有进展时留言一句话说明。
2. 交付时，在 issue 下留言，写明：交付物路径、PR 编号、需要谁审核或决定。
3. 项目总监审核后，在 issue 下留言结论：通过 / 需修改 / 阻塞。
4. 产品设计类 issue：项目总监通过可行性评估后，结论上报真人；真人确认后，由项目总监关闭 issue。
   架构类 issue：项目总监审核通过后关闭。
   岗位不自行关闭 issue。

### 4.3 依赖关系（硬性条件）
- 架构师的实现任务（#8、#11、#14、#17、#20）必须同时满足：
  1. 对应学科的产品设计 issue 已通过（#7、#10、#13、#16、#19）；
  2. 总体技术方案 #1 已通过。
- 两个条件缺一不可。在此之前，架构师只能做调研和草案，不得开始实现。
- 学科架构师需要使用共享能力时，先在 #23 中提出需求，等共享能力架构师回复排期和接口后再开工。不得直接修改 `packages/shared/` 下的共享代码。

## 5. PR 的用法

- **分支名**：`feat/<学科>-<主题>-<issue号>`，例如 `feat/english-product-design-7`。
- **PR 标题**：`[学科][岗位] 内容（状态）`，例如 `[英语][产品设计师] 产品设计与学段梳理（待审核 v1.0）`。
- **文件位置**：产品文档放 `docs/product/`，架构文档放 `docs/architecture/`，学科代码放 `apps/<学科>/`。
- **PR 描述**：写明关联的 issue（使用"Refs #7"，不要用"Closes"，关闭权在项目总监），列出交付清单和需要审核的问题。
- **审核意见**：直接写在 PR 的评论里，或指向具体文件和行。作者在同一个 PR 中修改，不另开 PR。
- **合并**：只由项目总监合并。作者不合并自己的 PR。

## 6. 提问与决定

- **问别人**：在对方岗位的 issue 下留言，开头写清楚问题和所需答复的时间点。
- **需要决定的事**：在相关 issue 下标注 `needs-decision` 标签。
- **需要真人处理的事**：在相关 issue 下标注 `needs-human` 标签。真人的待办入口是筛选 `label:needs-human` 的 open issue，见第 10 节。
- **跨学科问题**：写在 #1 下。
- **决定分级**：
  - **小事**（在已批准的范围内调整关卡数值、文案等）：产品设计师与项目总监决定，在 issue 中记录。
  - **中事**（改变学科的学习路径或游戏机制）：项目总监决定，每天 19 时汇总给真人。
  - **大事**（学段覆盖范围、未成年人相关功能、付费、AI 内容策略）：必须真人确认。
- **真人的审核节奏**：项目总监每天晚上 19 时汇总一次需要真人决定的事项，集中提交。紧急事项除外。
- **产品方案**：产品设计师与项目总监在 issue 中探讨可行性和优化，按上述分级决定。大事上报真人，真人确认后才定稿。
- **需要真人决定的事**：项目总监在 #1 下汇总，列出选项、建议和影响，真人回复后，项目总监把结论写回 #1，并同步更新相关文档。
- **决定的记录**：决定一经做出，写在 issue 评论中，并同步到对应文档（文档中增加"决定记录"段落）。

## 7. @ 提及规则

- 只 `@` 真实的 GitHub 登录名。目前只有 `jidoraku-admin`。
- 角色名、岗位名、学科名不使用 `@`，改用反引号，例如 `项目总监`、`产品设计师`，避免误发通知。
- 需要通知真人时，在 #1 下写明，不要用 `@` 指向非登录名。

## 8. 长内容的发布

- 超过几行的评论，先写入文件，再用 `gh api ... -F body=@文件路径` 发布，不要在命令行中直接拼接长文本。
- 发布后检查一次评论是否完整。若被截断，编辑原评论或发布更正评论，并在更正中注明"更正"。

## 11. 阶段接力（学科内）

每个学科的三个岗位按阶段接力，不同时启动。阶段由 issue 上的标签决定，同一时间只有一个阶段生效。

| 阶段 | 标签 | 谁可以动 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 设计中 | `stage:design` | 产品设计师起草；项目总监逐轮审核稿件并评估技术可行性 | 项目总监审核通过，把标签改为 `stage:design-final` |
| 待真人定稿 | `stage:design-final` | 真人 | 真人在 issue 中确认定稿，把标签改为 `stage:dev` |
| 开发中 | `stage:dev` | 学科架构师 | 功能完成，PR 通过审核 |
| 待验收 | `stage:acceptance` | 真人 | 真人验收通过 |
| 推广中 | `stage:promotion` | 运营 | — |

**硬性规则**
- 没有 `stage:design-final` 且真人已确认，架构师不得开始开发，不得提交功能 PR。
- 没有 `stage:promotion`（即真人验收通过），运营不得开始推广工作。
- 阶段只能向前推进。回退到前一阶段需要在 issue 中说明原因，由真人确认。
- 标签由当前阶段的负责人更新：设计审核通过由项目总监更新为 `stage:design-final`；真人确认定稿后更新为 `stage:dev`；验收通过由真人更新为 `stage:promotion`。

**设计阶段的分工（`stage:design`）**
- 产品设计师起草设计，在 issue 中提交稿件，并与项目总监逐轮讨论。
- 项目总监审核每一版稿件，评估技术可行性，给出修改意见。架构师和共享能力架构师可以被咨询，但可行性结论由项目总监给出。
- 项目总监认为稿件可行后，才把标签改为 `stage:design-final`，交给真人定稿。

**设计稿的审核标准**
项目总监审核时，每一版稿件都要从以下四个维度给出结论：

| 维度 | 审核要点 |
| --- | --- |
| 技术 | 能否在 Flutter、Flame、Rive、Lottie 上实现；是否依赖共享服务，依赖是否已就绪；AI 调用是否符合分层（题库、缓存、小模型、大模型）；工作量估计与风险 |
| 趣味 | 游戏循环是否清楚，玩家每 5–10 分钟是否有明确的小目标；升级、奖励、反馈是否及时；是否真的在玩，而不是换了皮的做题 |
| 故事 | 是否有统一的世界观和角色；关卡之间是否有连贯的剧情线；故事是否服务于知识点，而不是喧宾夺主 |
| 吸引性 | 目标用户（学段、年龄）是否清楚；首次体验是否在几分钟内能获得成就感；留存机制是否合理，且不依赖诱导或成瘾设计 |

**结论格式**：每一版审核在 issue 中给出四个维度的结论（通过 / 需修改 / 不可行），并列出具体修改点。四个维度都通过，才能进入 `stage:design-final`。

**定时任务的执行方式**
学科定时任务每次运行时先读取当前阶段标签，只执行该阶段对应岗位的工作。其他岗位直接跳过，不留下空的留言。
