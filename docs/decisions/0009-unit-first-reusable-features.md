# 0009 先做第一单元，功能复用，数据替换（2026-11-22）

- 决定人：项目总监（真人 2026-11-22 指示：每科先做一单元的功能，调通并丰富化后再导入其他单元的数据）
- 分级：中事（开发方式，不改变学习路径与游戏机制），由项目总监决定
- 关联：#68（六对话协调）、#25（每日汇总）、#7（英语）、#23（共通）、0007（起步学段）

## 背景

各科都要覆盖整册教材。若每个单元各自写功能，代码会按单元分叉，重复开发且难以维护。英语已经在 Unit 1–3 上各自实现了玩法，说明功能与数据耦合较深。

## 选项

1. 按单元并行开发：每单元独立做功能。缺点：代码重复，单元间风格不一致，测试成本随单元数线性增加。
2. 先做一个单元的完整功能，再导入其他单元：功能只写一次，数据以结构化文件替换。缺点：第一单元要做得更完整，前期进展较慢。

## 结论

采用选项 2，具体规则：

1. **每科只开发一个单元的功能。** 第一单元作为功能的验证对象，玩法、关卡、奖励、失败与补救都在这一单元调通，并做丰富化（动画、反馈、音效等）。
2. **功能是复用的，数据是替换的。** 单元内容以结构化数据（`index.json` + `unit*.json` + 素材）表示，应用按单元代码加载，不写死单元。
3. **导入其他单元不改代码。** 第二个单元的数据导入即可运行；若需要改代码，视为功能的抽象不完整，需要回到第一单元修正抽象。
4. **只有定稿后才开发。** 未经总监定稿的学科（数学、语文、物理、化学）按 #68 的规则不进入开发。
5. **英语的现状。** 英语已有 Unit 1–3 的代码。从本决定起，新增的单元专属代码不再合入；Unit 2–3 作为数据导入的验证对象，保留现有功能。

## 影响

- 每科的验收标准：第一单元的功能完整调通，并且第二个单元的数据能在不改代码的情况下运行。
- 共通（#23）的共享组件也按此验证：展示组件与契约要能服务于不同单元的数据。
- 每日汇总（#25）按单元进度而非单元数量汇报。
